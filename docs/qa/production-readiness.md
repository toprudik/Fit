## 1. Как проверяем, что тесты ловят ошибки

Тест считается полезным, только если он падает, когда код сломан. Поэтому мы намеренно портим код по одной строке (мутация) и смотрим, упадёт ли хоть один тест.

- [x] Фронт, 22 модуля бизнес-правил, 89 мутаций: тесты поймали 57 (64%). Для выживших написаны тесты `*.edge.test.ts`, список ниже в разделе 3.
- [x] База, функции денег: мутации `private.pick_pass`, `private.post_charge`, `private.pass_next_share` прогнаны против всех 111 файлов pgTAP. Ни один тест не замечал, что абонемент выбран истёкшим, замороженным по местной дате тренера, отменённым, без остатка или не того вида. Эти правила PRD 2.8-7 теперь закреплены в `supabase/tests/978_qa_money_booking.test.sql`.
- [ ] База, остальные функции: прогнать те же мутации по записи (`book_slot`, `decide_booking`, лист ожидания), заморозкам и долгам.
- [ ] Повторять мутационный прогон перед бетой 24.11 и после каждой крупной волны правок.

Как повторить для SQL: `scripts/qa/sql-mutate.py` берёт последнее определение функции из `supabase/migrations`, меняет одну строку и прогоняет тесты внутри их транзакции, база не меняется. Пример запуска в шапке скрипта.

## 3. Найдено, ждёт решения или следующего прохода

- [x] Лимит долга не ограничивал самозапись в долг: считались только уже списанные занятия, запросов можно было слать сколько угодно. По решению пользователя 18.10: без разрешения одна запись в долг за раз и через подтверждение, с разрешением без подтверждения до числа, которое задаёт тренер. Тест `979_debt_limit` (24 проверки), мутации пойманы.
- [x] `create_pass` и `record_past_session` при двойном нажатии создавали два абонемента с двумя оплатами или два прошедших занятия с двумя списаниями. Теперь форма продажи передаёт ключ запроса, и повтор с ним возвращает уже проданный абонемент (в том числе при двух параллельных вызовах). Повтор прошедшего занятия с тем же началом возвращает первое. Тест `996_money_retry_safe`, мутации пойманы.
- [x] Продажа абонемента падала с `ledger_invalid`, если в ту же секунду тренер прощал тот же долг. `settle_debt` теперь перепроверяет каждое списание после блокировки и пропускает прощённое. Проверено на двух соединениях: продажа проходит, прощённый долг не гасится. В pgTAP это не воспроизвести, в одной транзакции проверка совпадает с фильтром цикла.
- [x] Помощник с правом «оплаты» не может подтвердить платёж. Не ошибка: права `passes` и `payments` помощнику не выдать (правило 3 PRD волны 3, ограничение в `20261017090713_delegations.sql`, `ASSISTANT_SCOPES`), так что такого помощника не бывает.
- [ ] Добавление участника сверх группы (`add_group_participant_extra`) занимает место, придержанное для листа ожидания.
- [ ] Замеры, история тренировок, занятия клиента: списки ограничены 1000, 50 и 300 строками без «Показать ещё». У давнего клиента пропадают старые данные.
- [ ] Экспорт аккаунта читает страницами без сортировки, на больших таблицах возможны повторы и пропуски строк.
