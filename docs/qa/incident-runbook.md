# Что делать, если в проде что-то сломалось

Порядок действий на время беты. Цель: быстро остановить вред, сохранить деньги и данные клиентов в порядке, потом разбираться. Чек-лист готовности: [`production-readiness.md`](production-readiness.md).

## 1. Понять, что сломалось

| Симптом | Где смотреть |
|---|---|
| Сайт или мини-апп не открывается | Vercel, проект `dafit-web`, вкладка Deployments: статус последней сборки, затем Logs |
| Ошибка на экране у пользователя | Sentry, когда он включён; иначе Vercel Logs по времени обращения |
| Бот молчит | Vercel, проект `dafit-bot`, Logs; в BotFather бот не заблокирован |
| Не приходят уведомления | Supabase, SQL: `select status, count(*) from notification_outbox where created_at > now() - interval '1 hour' group by 1` |
| Занятия не завершаются, не списываются, лист ожидания стоит | Supabase, SQL: `select jobname, status, start_time, return_message from cron.job_run_details d join cron.job j using (jobid) order by start_time desc limit 30` |
| Неверные суммы или остатки абонементов | Supabase, таблица `ledger_entries` по паре; журнал не удаляется, каждая операция видна |

## 2. Остановить вред

### Первые 10 минут после плохого релиза

Кто: Rudik. Если его нет рядом, Claude в чате проекта может откатить сборку через коннектор Vercel, но только по его команде в чате: это изменение прода. Доступ к Supabase и GitHub есть только у Rudik.

1. **Минута 0–2. Что вышло последним.** GitHub → Actions: какие workflow прошли после последнего мёржа в `main`. Если был «Database deploy», значит менялась база (шаг 4). Если нет, сломан код (шаг 2 или 3).
2. **Минута 2–4. Откатить веб.** Vercel → `dafit-web` → Deployments → предыдущая сборка с меткой Production, которая работала → «⋯» → Instant Rollback. Через минуту открыть https://dafit-web-eight.vercel.app и мини-апп в Telegram. База при этом не меняется.
   - На плане Hobby откат возможен только на предыдущую боевую сборку. Если сломано две сборки подряд, вместо отката сделать в GitHub Revert плохого PR и смёржить его, сборка займёт около 3 минут.
   - После отката Vercel перестаёт сам выкладывать новые коммиты из `main`. Когда исправление смёржено, вернуть: Deployments → новая сборка → «⋯» → Promote to Production (или Undo Rollback). Иначе следующий мёрж молча не выйдет.
3. **Минута 4–5. Откатить бота**, если менялся `apps/bot`: Vercel → `dafit-bot` → Deployments → предыдущая сборка → «⋯» → Instant Rollback. Webhook трогать не надо, адрес бота не меняется. Проверка: `/start` в @fitconnection_bot отвечает кнопкой.
4. **Минута 5–8. Если сломала миграция.** Миграции назад не откатываются, а откат веба на старый код при новой схеме может сломать ещё больше: откатывать веб только если ошибка точно в коде. Сначала остановить фоновые задачи, чтобы они не множили вред (списания, рассылки, лист ожидания). Supabase → SQL Editor:

   ```sql
   update cron.job set active = false where active;
   select jobname, active from cron.job order by 1;
   ```

   Это останавливает все задачи pg_cron, ничего не удаляя: завершение и списание занятий, напоминания, рассылку уведомлений, лист ожидания, отчёты. Пока они стоят, записи и оплаты в приложении работают, но уведомления копятся в очереди и занятия не закрываются. Дальше исправление новой миграцией через обычный PR, «Database deploy» накатит её после мёржа. Потом включить задачи обратно:

   ```sql
   update cron.job set active = true where not active;
   ```

   Очередь уведомлений после этого разойдётся сама; устаревшие сообщения о записях и подменах `claim_outbox` пропускает.
5. **Минута 8–10. Сообщить** (раздел 3) и записать время, когда сломалось и когда откатили.

Восстановление базы из бэкапа не входит в эти 10 минут. Бэкап делается раз в сутки (в 03:37 МСК, репозиторий `fit-backups`), поэтому восстановление поверх прода стёрло бы всё, что пользователи сделали с ночи. Он нужен только при потере данных: копию поднимают в отдельный пустой проект Supabase (`scripts/db-backup/restore.sh`, см. `docs/deployment.md`) и оттуда переносят потерянные строки. Это делается не спеша и вместе с Claude.

### Другие случаи

- Шлются ошибочные уведомления: остановить только рассылку, `update cron.job set active = false where jobname = 'notifications-dispatch'`, после исправления `active = true`. Остальные задачи продолжают работать.
- Неверные списания: не удалять строки. Тренер прощает списание в интерфейсе («Простить»), для многих строк пишется миграция с `waive_entry`. Так история денег остаётся честной.
- Утёк секрет: сразу перевыпустить ключ (BotFather для бота, Supabase для ключей базы, Vercel для `CRON_SECRET`), обновить переменную в Vercel и пересобрать. Правила в ADR 0002.

## 3. Сообщить

- Пользователям беты: один пост в канале или рассылка через бота, что случилось и когда починим. Без технических подробностей и без личных данных.
- Если затронуты личные данные: по 152-ФЗ уведомить Роскомнадзор в течение 24 часов о самом инциденте и в течение 72 часов о результатах расследования; по GDPR надзорный орган в течение 72 часов. Порядок готовит тред юридических документов.
