# Что делать, если в проде что-то сломалось

Порядок действий на время беты. Цель: быстро остановить вред, сохранить деньги и данные клиентов в порядке, потом разбираться. Чек-лист готовности: [`production-readiness.md`](production-readiness.md).

## 1. Понять, что сломалось

| Симптом | Где смотреть |
|---|---|
| Сайт или мини-апп не открывается | Vercel, проект `dafit-web`, вкладка Deployments: статус последней сборки, затем Logs |
| Ошибка на экране у пользователя | Sentry, когда он включён; иначе Vercel Logs по времени обращения |
| Бот молчит | Vercel, проект `dafit-bot`, Logs; в BotFather бот не заблокирован |
| Не приходят уведомления | Supabase, SQL: `select status, count(*) from notification_outbox where created_at > now() - interval '1 hour' group by 1` |
| Занятия не завершаются, не списываются, лист ожидания стоит | Supabase, SQL: `select jobname, status, start_time, return_message from cron.job_run_details d join cron.job j using (jobid) order by start_time desc limit 30` |
| Неверные суммы или остатки абонементов | Supabase, таблица `ledger_entries` по паре; журнал не удаляется, каждая операция видна |

## 2. Остановить вред

- Сломала последняя сборка веба: Vercel, Deployments, предыдущая рабочая сборка, меню «⋯», Promote to Production. Это откат за минуту, база не меняется.
- Сломала миграция: миграции назад не откатываются. Пишется новая миграция с исправлением, проходит обычный PR и CI, «Database deploy» накатывает её после мёржа.
- Шлются ошибочные уведомления: остановить задачу рассылки в Supabase SQL `select cron.unschedule('notifications-dispatch')`. После исправления вернуть тем же вызовом `cron.schedule`, что в миграции `20261015220000_notification_dispatch.sql`.
- Неверные списания: не удалять строки. Тренер прощает списание в интерфейсе («Простить»), для многих строк пишется миграция с `waive_entry`. Так история денег остаётся честной.
- Утёк секрет: сразу перевыпустить ключ (BotFather для бота, Supabase для ключей базы, Vercel для `CRON_SECRET`), обновить переменную в Vercel и пересобрать. Правила в ADR 0002.

## 3. Сообщить

- Пользователям беты: один пост в канале или рассылка через бота, что случилось и когда починим. Без технических подробностей и без личных данных.
- Если затронуты личные данные: по 152-ФЗ уведомить Роскомнадзор в течение 24 часов о самом инциденте и в течение 72 часов о результатах расследования; по GDPR надзорный орган в течение 72 часов. Порядок готовит тред юридических документов.

## 4. Разобрать после

Короткая запись в `docs/qa/incidents/ГГГГ-ММ-ДД.md`: что случилось, сколько пользователей задело, как нашли, что сделали, какой тест теперь ловит эту ошибку. Без теста инцидент не закрыт.
